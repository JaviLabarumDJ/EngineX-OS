## Observed experiments

All generation and sandbox work ran on the ARM64 build host, inside scopes with `MemoryMax=6442450944` and `MemorySwapMax=0`. The loop files, unpacked image, fixture output and private Go cache were on disk under `/var/tmp/s140-prime4`, never `/tmp`. Mount/network/PID namespaces plus chroot isolated Engine; reset/update/reboot/encryption commands were shimmed. No real deck was contacted.

Fixtures use `internal/testlibrary.Create` and its captured Engine DDL. The richer fixture includes 6,000 short WAV files from `internal/testaudio`, 6,000 performance records encoded by `analyzer.PerformanceBlobs`, 6,000 large artwork rows and a valid library UUID. Its `m.db` is 743,661,568 bytes, on a 2 GiB exFAT loop image. These are synthetic records, not the reporter's data.

A separate 1 GiB exFAT fixture uses small covers plus the captured `ENGINE-5.0.4-hm.db-schema.sql`, with 500 history sessions and 6,000 history tracks.

A sandbox-only D-Bus USB-SATA classification mock was also attempted. It received no device-query calls and Engine did not open the SSD; this is not counted as an attachment test. A later SQLite check of the synthetic SSD returned `quick_check=ok`, with 6,000 rows each in `Track`, `PerformanceData` and `AlbumArt` and schema 3.0.2.

The 56/58-second figures measure the full render probe, which navigates settings; they are not measurements of when the first frame appeared. These are build-host observations, not predicted deck timings or proof of spare repair budget on a slower deck. CPU, storage and strace overhead differ. `strace -f` and Engine thread `/proc` stack snapshots were collected. Live cgroup readback confirmed the 6 GiB limit and zero OOM kills in the recorded runs. None supplied a stuck Engine stack matching #140.

Early harness failures (unshimmed encryption, an autocleared loop during remount, an undersized fixture disk, a recorder's default idle timeout) were corrected and excluded from product conclusions.

## Inference and unknowns

**Supported exclusions, within those inputs:** the guardian does not inevitably hang because a library has 6,000 tracks; reaching its repair deadline does not inevitably prevent mounting or opening that database **as Engine's internal library**; the tested SQLite hook and UI pack can initialize with this SSD binding. The external-media ATTACH path was not exercised. No `database/sql` transaction/connection self-deadlock was found in the independently reviewed `pkg/dbhealer` code; the review does not constitute runtime validation of all other inventory rows.

**Most suspicious remaining paths:** the reporter's exact `m.db`/`hm.db` and persistent `/data` state; the real edisksd-to-Engine media attachment; hardware-dependent native initialization or USB-SATA I/O. Cold QML compilation on the deck is also unmeasured: a hard power-off makes the next boot clear its cache again, so another cold attempt is not a warm-boot test. A child stuck in kernel uninterruptible I/O could keep the hook's final `waitpid` blocked despite SIGKILL, but no such I/O stall was observed. Simply returning early while that writer remains alive would violate the rule against concurrent external writes to an Engine-open library.

Another review concern is that the data-only path still calls history pruning, whose `Tune`/`PRAGMA optimize` and compaction can affect `hm.db`. The healthy history fixture booted and had no `sqlite_stat1` afterward. This was not demonstrated as the hang and was not changed as an unrelated speculative fix.

**Still unknown:** actual filesystem, SSD size/free space/health, library schema/reserve bytes/journals, history and artwork sizes, drive profile, saved EngineX settings, the failing process/thread and its last error. Only exFAT was exercised; FAT32, NTFS and the HFS+ sidecar path were not. Fresh synthetic `/data`, offscreen rendering and loop devices cannot establish these facts. Repeated five-minute hangs do not prove UI safe-mode was reached: the guard's 15-second timer can clear the boot-token while a process remains active with a hung UI.

## Next reporter evidence

1. Do not factory-reset or erase the library to investigate this. A powered-off boot with the internal SSD temporarily disconnected, if the owner can do this safely, is the smallest useful discriminator. Record whether the same image then reaches the UI.
2. If that boots, note the console code and enable ordinary authenticated diagnostics while the UI works. Preserve the library before opening it in desktop software or running repairs: obtain the filesystem, drive capacity/free space, presence/size of `hm.db`, and a private copy of `Engine Library` or at least `Database2` (including any journals) with the owner's consent. Record database/journal timestamps and sizes, plus any `.pre-reserve` or `.reserve-rebuild` files. Opening the database can recover a journal and change that evidence. It can contain private track/history information. Do not run filesystem repair or SQLite VACUUM on the only copy.
3. If the same image still hangs without the SSD, prioritize persistent `/data` and JC11 hardware/UI startup. SSD content alone would then be insufficient to explain the symptom.

The image has a stock `/usr/Engine/Scripts/writeJournalctl.sh`: given a mounted device name, it writes the journal to `/media/<device>/Engine Library/logs/YYYY-MM-DD__HH-MM-SS.log.gz`. Existing exports there can be copied off the SSD without a console code. No way to trigger that script from the stuck splash screen was verified, and those files must not be assumed to contain the current failed boot.

No existing log-download method usable from the LAN without the console code was verified. Owner console controls require authentication; internal control routes are restricted to loopback. The image's journald configuration is volatile, so a power cycle loses the preceding boot's journal. Documentation mentioning service logs does not prove a public log endpoint. No SSH default, authentication bypass, new diagnostic backdoor or release was added.
